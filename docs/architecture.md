# Architecture

## The idea

The Android versions of Dragon Quest IV, V and VI are each made of two layers:

- **the engine**, `libdq4core.so` (`libdq5core.so`, `libdq6core.so`): a C++ library compiled for ARM64 that contains the whole game (scripts, battles, menus' logic, saves);
- **a Unity layer** (`libil2cpp.so`, C#) that displays what the engine asks for, plays the sounds and sends the touch input back.

The port keeps the engine exactly as it is and replaces the Unity layer:

```
 your APK files                      dq456_pc (Python)
 ┌──────────────────┐   read   ┌────────────────────────────────────────────────────────────────┐
 │ libdqNcore.so    │ ───────► │ core/emu_core.py   Unicorn: loads the ELF, emulates libc,     │
 │                  │          │                    OpenGL texture uploads and file access      │
 │ Unity data       │ ───────► │ world/             maps, sprites, 3D models, sounds (UnityPy) │
 └──────────────────┘          │ core/engine.py     steps the engine, decodes its packets      │
                               │                    (what it asks of Unity), sends input back   │
                               │ window/, menus/    pyglet + OpenGL: draws scenery, sprites,   │
                               │                    windows, effects; keyboard, mouse, gamepad  │
                               └────────────────────────────────────────────────────────────────┘
```

Every frame, `window/game.py` runs one or more engine steps (`Engine.step`), then draws the state decoded from the packets the engine wrote for Unity (`core/pktlog.py` splits them, `core/engine.py` `State` keeps the result: camera, sprites, map, fades, windows, sounds). Input goes the other way: key masks for the engine's `GameUpdate`, and menu messages on the same queue the Unity `MenuPort` uses.

The engine is never modified on disk. The few in-memory patches and hooks the port needs are listed, with their guards, in [`engine-patches.md`](engine-patches.md).

## Several games

The three games are built the same way: an ARM64 engine behind the same Unity layer (same Unity version, the same drawing commands, plus a few in DQ V and VI, the same file formats). The port is one code base with one profile per game (`dq456_pc/games.py`: folder name, engine library, name, whether this version runs it). The game is chosen before anything else is imported, by the environment variable `DQ_GAME` (set by `launch_dq4.bat`, `launch_dq5.bat`, `launch_dq6.bat`, which call the shared launcher `tools\launch_game.bat`) or by `python -m dq456_pc --game dq5`. `paths.py` gives each game its own APK, saves and cache folders; the settings are shared. The three games run; a game a version would not run only has its files checked (exit code 3).

The engines of DQ V and VI are a newer version of DQ IV's: most C++ classes moved into namespaces (`fld::`, `twn::`, `menu::`, `ardq::`...), the static variables moved, the game parts and the drawing commands are numbered differently. `core/engine_layout.py` holds these differences: the packet and part numbers are translated to DQ IV's (the rest of the port keeps them), and the addresses of the static variables the port reads are found in the code of the exported functions that use them (the same search gives DQ IV's known addresses back). `Core.export` also finds a name without its first namespace (a variable inside a namespace by its plain name). DQ VI numbers its game parts one higher than DQ V and keeps DQ IV's layout for the message canvas (`SDrawCTRL`, read in `CanvasSetup`); its adventure logs hold no unique game ID. Its title screen flies over the clouds with a map camera movement before the engine sends any camera of its own (the window draws with the movement alone), and its sky, world map and sea, made for the portrait screen, are continued by mirror copies on both sides (`EXTENDED_SKIES`); its adventure log list uses frames 239 to 241 where DQ IV and V use 219 to 221. DQ VI draws its world map as meshes of 25-column tile rows: the engine sends where each mesh goes and computes their texture coordinates itself (`FieldData::setMeshInfo`, called by the port), the tiles come from the world's own atlas (`field<type>`); its place icons have their own texture (`symbol`) and only 21 slots on the Unity side, so the window in which the engine shows them only grows to what a 21:9 screen shows (DQ IV and V: 114 slots, the window covers everything).

The window layout reader (`tools/ui_il2cpp`) finds what it needs in each game's own `libil2cpp.so` (`addresses.py`: methods by name and signature, the IL2CPP runtime helpers, segments, static fields by name) and follows the linker's branch islands as part of a function.

Their Unity layer draws a few things DQ IV's did not need, reproduced for DQ V's title screen: a map's camera movements (packet 6 >= 0x1000, `FldObject.SetCameraNo`: the FEMV block of the map places the view instead of the engine's camera; `world/map_objects.py`, `window/camera.py`), the orthographic layer (packet `cmd_mesh_ortho`: logos and title texts drawn flat over the scene, `SceneCamera.s_DSSAOrthoCamera`), the map's own background color (FETC, until a packet 8), the free camera mode of `cmd_fld_load`, and the texture coordinates of their meshes (`MeshChara`: texture scale (1, -1), offset (0, 1)). These are only enabled for DQ V and VI (`engine.ENGINE_V2`). Their `cmd_mesh` also shows the mesh it fills (`MeshChara.SetVisible(true)`). DQ V's Slime Touch (the casino's mini-game) has its own menu port (category 5, `SlimeTouchPort`): the engine draws the game on the orthographic layer, Unity adds touch boxes and animated prefabs (countdown, "Game Over", target boards) read like the `fbx` models (`core/slime_touch.py`, `window/slime_touch.py`, `Data.prefab_model`). DQ VI's slime curling draws a 3D scene of its own; its two ports of category 5 (`SlimeCurlingPort`) only give the engine the touch screen and the place on the screen of a point of the world (`core/slime_curling.py`, `window/slime_curling.py`); the window then shows the phone's whole height, the sides beside the phone's column showing that column stretched and blurred (DQ V's slime race too). DQ V's world map adds a crater and three puffs of smoke over the mountain's icon (Unity's `Volcano`: `world/volcano.py`). DQ V's T'n'T board (the engine's "sugoroku") is played by the engine in the board's town map: its squares are one mesh with the `Custom/DssaNormal` shader (MeshChara shader 4: drawn with the scenery, in the map's coordinates, kept until the engine sends it again), and the direction arrows are the icons of a window placed in the scene by position and turn arrays (`core/sugoroku.py`, `window/sugoroku.py`); the player pushes the direction of an arrow (keys, or a click on it). Their rules of a game (Difficulty, Cheats) use the same engine values at their own places (`engine.py`: `REWARD_READERS_V2`, `DAMAGE_V2`, `COUNTDOWN_FN_V2`, `LEVELUP_V2`, `HEAL_V2`): their victory message reads the battle's totals before they are shared out, so the first reader multiplies them; DQ VI draws no game ID, the port writes one at a new game (`GameStatus::resetUniqueID`, saved in the adventure log at 0x14). The casino's wins are multiplied at their own places too (`CASINO_WINS_V2`: slot payout, poker, DQ V's monster arena). The battle history reads the same structures at other offsets (`battle_history.LAYOUTS`; DQ VI's battle code is split into `BattleTask` tasks), play time follows the game speed from `GameUpdate` (`PLAYTIME_V2`), and a monster's copy of a character is named as in DQ IV (`COPY_PREFIX_V2`). Some DQ IV fixes have nothing to do there: their Magic menu already says a healing spell would be of no use instead of casting it, the French patch gives the status names their article, the log in cyan at the church is the last one saved, kept in a file (`SaveLoad::setSaveBank`), and fades keep their game duration. Their new game has the same panel as DQ IV's, without the gender (their hero is a boy). Their randomizer changes the items and the monster drops (`randomizer/items.py`, `GAMES`: their map files keep the furniture table at another place, rows of 0x14 bytes; their item gifts have their arguments from + 8; the people's gold and tokens keep their kind, only their amount changes; the bestiary stays the game's; `Engine._item_hooks_v2`) and their encounters and bosses (`randomizer/encounters.py`, `V2`, `Catalog.from_files`: their zones and boss parties are read from the game's tables, `assets/leveldata/dq?ds_encount_data.dat` and `encount_special.dat`, args::ExcelBinaryData files with a header of 20 bytes; their bosses are the monsters their bestiary leaves out (`book_data.dat`), their boss fights the rows their scripts start whose party holds one, the fights the story needs lost kept; `Engine._encounter_rando_hooks_v2`, `BREW_V2`: the groups are rewritten in `Encount::brew` before the game fits them on the screen).

## The `data` folder

Everything that belongs to the player stays in `data` (or the folder named by `DQ_DATA`), never in the repository:

```
data\apk\dq4\en-us\  fr-fr\ ... the APK files, one folder per language code (dq5\, dq6\: the other games)
data\saves\dq4\                 data1.dat ... data5.dat, data9.dat (the game's adventure logs), savestates\ and rules\ (dq5\, dq6\: the other games)
data\cache\dq4\fr-fr\ ...      what the port computes from the APKs of each game and language (maps, sprites, sounds, window layout): safe to delete
data\settings\                  settings.json (shared by the games) and the history
data\logs\                      window_errors.log
```

Files left by older versions of the port (French folder names, older layouts) are moved into this layout at startup by `paths.migrate`, without deleting or overwriting anything.

## Texts and languages

The game's own texts come from the APK of the chosen language and are never touched; a language without APK files of its own runs the English ones (otherwise the French ones), its port texts staying in that language. The port's texts are keys: the code calls `tr('saves.export_saves')`, and module constants mark their keys with `N_()` so that they are translated when drawn (the language can change while the game runs); a key missing in a language, or a language file that cannot be read, shows the English text (the only fallback; the game's APK files fall back on English, then French). The texts are one JSON file per language, `dq456_pc/languages/<code>.json` (`language.read_file`): its own name, its flag, then one entry per text with its key, the English text (`en`, the reference) and the text displayed (`text`; empty, or not fitting the English one: English is shown); any `<code>.json` there is a language. The language screen adds one (`language.create_language`: every English text, empty translations) and reads a file again after it is edited (`language.check_language`); its add-language screens are in English only (keys `new_language.*`, only in `en-us.json`). Each language is drawn with fonts that have its letters (`language.font_families`: the game font for the Latin and Japanese letters, the system fonts for Korean and Chinese); help texts are wrapped between characters in Japanese and Chinese (`language.wrap`). `tests/test_language.py` checks that every language has the keys of the English file in its order and its English texts in `en`, the same placeholders, edge spaces and line breaks, no French in the English texts, and that every key used by the code exists and every key is used.

## Tests

`tools/run_tests.sh` runs every test file in its own process and lists the skipped tests at the end. Most tests need nothing (fake engine, fake window); the ones marked "real engine" load the game from `DQ_APK`. GL drawing tests need an OpenGL context (pyglet "headless" mode on Linux, set by the runner).
